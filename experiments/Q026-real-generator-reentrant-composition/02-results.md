## Round 1 — real result

Passed, after one honest correction (see "Corrections" below). The **actual, unmodified**
`Myriad.Plugins.LensesGenerator`, loaded via `Assembly.LoadFrom` and discovered via the real
`MyriadGeneratorAttribute` scan (not a direct constructor call), invoked against the real on-disk
`Person.fs`, and formatted through the real `ParsedInput.ImplFile`/`CodeFormatter.FormatASTAsync`/
`Generation.getHeaderedCode` pipeline, produced:

```fsharp
//------------------------------------------------------------------------------
//        This code was generated by myriad.
//        Changes to this file will be lost when the code is regenerated.
//------------------------------------------------------------------------------
namespace rec Domain

module PersonLenses =
    open Domain

    let Name =
        (fun (x: Person) -> x.Name), (fun (x: Person) (value: string) -> { x with Name = value })

    let Age =
        (fun (x: Person) -> x.Age), (fun (x: Person) (value: int) -> { x with Age = value })
```

Durable copy: `artifacts/round1-output/PersonLenses.fs`. Structurally this matches Q010's own
hand-typed stand-in almost exactly (same tuple-of-lambdas shape, same non-piped setter argument
order, same nested-module naming convention) — a real, if retrospective, point of reassurance that
Q010's stand-in was a faithful transcription, not just a convenient guess.

## Corrections discovered while running (reported honestly, not patched over silently)

1. **Round 1 initially failed** with `FileNotFoundException: EditorConfig.Core` when
   `EditorConfig.readConfiguration` ran inside the harness. Root cause: `Myriad.Core.dll` is
   referenced via a raw `<Reference HintPath>` (matching Q019's own established pattern for
   referencing Myriad.Core from a scratch project), which does not pull in Myriad.Core's own
   transitive NuGet dependency (`editorconfig`, the actual package ID — `EditorConfig.Core` does
   not exist on the configured feeds and fails with `NU1101`) the way a `ProjectReference` or the
   real CLI's own build does. Fixed by adding `<PackageReference Include="editorconfig"
   Version="0.15.0" />` directly to `Harness.fsproj`. This is real, if shallow: it shows that
   invoking Myriad's real formatting pipeline (not just its generator logic) outside `Program.fs`'s
   own build graph has a genuine, if fixable, packaging friction point — a from-scratch host needs
   to know and supply the real CLI's full transitive dependency set, which NuGet's own project
   graph gives `Program.fs` for free and a raw `HintPath` reference does not.
2. **Round 2 initially left 2 `Error`-severity diagnostics** on `Person.fs` itself (`The namespace
   or module 'Myriad' is not defined`, `The namespace or module 'Generator' is not defined`) —
   `checker.GetProjectOptionsFromScript` builds project options with no reference to
   `Myriad.Plugins.dll`, so FCS's own type-checker (a separate concern from `LensesGenerator`'s own
   Fantomas.FCS-based *untyped* parse, which never needed this) cannot resolve `Person.fs`'s `open
   Myriad.Plugins` / `Generator.LensesAttribute` usage. `01-design.md`'s own verification bar only
   required zero errors on `fileB`/`fileC`, not `fileA` — so this was not a pre-registered failure
   — but it was fixed anyway, for a materially cleaner result, by appending `-r:<path to
   Myriad.Plugins.dll>` to `opts.OtherOptions`. Reported here rather than silently folded into the
   design as if it were always planned.

Neither correction touched the reentrant mechanism itself, `LensesGenerator`, or
`ReentrantJsonGenerator`'s logic — both were project-options/packaging fixes in the harness.

## What a review should press on

- **The reentrant-callback sentinel proves the callback fired, not that it fired while genuinely
  mid-flight rather than landing on an already-idle checker** — the identical scope limitation
  Q010's own review named in its Objection 1, inherited unchanged here since this quartet reuses
  the same mechanism and adds no new instrumentation for it.
- **`Assembly.LoadFrom` instead of `McMaster.NETCore.Plugins.PluginLoader` is a disclosed
  simplification, but its consequence for the `Q026.Bridge` side-channel specifically was never
  tested.** `src/Myriad/Program.fs`'s real plugin loading sets `config.PreferSharedTypes <- true`
  on an isolated `AssemblyLoadContext` per plugin. If a future integration used real ALC isolation,
  it is not obvious the harness's own loaded copy of `Q026.Bridge.dll` and
  `ReentrantJsonGenerator.dll`'s statically-referenced copy would resolve to the *same* static
  module instance across an ALC boundary — if they don't, the mutable side-channel breaks silently
  (the generator would see `Checker = None`). This quartet's plain-`Assembly.LoadFrom` approach
  cannot surface that failure mode one way or the other; it is untested, not ruled out, and
  directly overlaps `BACKLOG.md` item 2 (FSI/plugin-loading under ALC isolation, untested since
  Q003).
- **One record shape, two primitive fields, one dependency direction.** `Person` has no nested
  attributed type, no DU-based lens, no larger field count. This says nothing about whether the
  composition mechanism generalizes past this shape — it wasn't tested. The dependency direction
  tested is the one Myriad's real usage actually needs (a later generator consuming an earlier
  one's output) and matches Q010's own scope exactly; mutual/circular cross-generator dependency
  remains untested here as it was in Q010.
- **No cost/timing was measured at all.** This quartet's own question was purely "does the
  composition mechanism work," not "is it cheap" — unlike Q023/Q024, there is no keystroke-cost
  claim to make or scope here, and none should be inferred from this result.
- **The `Domain` namespace and the `"person"`→`namespace=Domain` config mapping were supplied by a
  hand-written function in the harness (`personConfigHandler`), not a parsed `myriad.toml` file.**
  This is real (the same `ConfigGetter: string -> (string*obj) seq` signature `Program.fs` itself
  calls), but the mapping's content was chosen by this quartet's own author, not read from an
  external config file the way a real project would supply it. Worth naming so it isn't mistaken
  for a full myriad.toml round-trip test.
- **The central, load-bearing scope limitation, restated from `00-hypothesis.md` because it is the
  answer to `BACKLOG.md` item 22's actual question, not a footnote:** this demonstrates the
  composition mechanism works when hosted in a **new, standalone process** built for this quartet.
  `src/Myriad/Program.fs`, read directly and unchanged this session, remains a short-lived,
  per-invocation process with no `FSharpChecker` anywhere in it and no persistent state across
  invocations. Nothing here shows Myriad's actual shipping CLI can host this today — turning it
  into that kind of host (the deeper ask behind item 22's full "reimagined" vision, and a
  precondition for item 19's live-save watcher ever composing with this) is a distinct,
  unattempted architecture change, not a natural extension of what this quartet built.
- **The `IMyriadGenerator.Generate` interface gap is real and was worked around, not closed.** A
  future integration that wants a generator to reentrant-query another file's typed content without
  a bespoke static-mutable side-channel per attempt would need `GeneratorContext` (or a new,
  optional interface, mirroring `IMyriadGeneratorWithDiagnostics`'s own opt-in extension pattern)
  to actually carry a checker/options handle. This quartet's `Q026.Bridge` is a workable spike-level
  stand-in for that, not a proposal for what the real API should look like.
